
# 06. M&A 보고서 검증 강화 및 재작성 안정화

- **개발 주제:** 경영자문 Agent의 LLM 보고서 사실 검증 및 재작성 처리 개선
- **개발 목적:** AI가 생성한 보고서의 수치·권고·인수 조건을 실제 Workflow 결과와 일치시키고, 검증 실패 시 불필요한 Tool 재호출 방지
- **주요 개발 내용:** 종합 보고서 검증 강화, 개별 Persona 및 What-if 보고서 검증, LLM 기반 재작성, 실행 이벤트 처리 개선, 코드 정리
- **진행 시기:** 2026년 11월 초 (05 기능 구현 이후)

## 1. 개발 목적

기존 경영자문 Agent는 M&A 평가 Tool의 결과를 바탕으로 LLM이 최종 자연어 보고서를 생성하였다.

그러나 LLM이 보고서를 작성하는 과정에서 일부 수치를 누락하거나, 평가 조건을 변경하거나, 실제 Tool 결과와 다른 설명을 생성할 가능성이 있었다.

또한 검증 실패 시 전체 Agent Workflow를 다시 실행하면 이미 확인한 M&A 평가 Tool이 중복 호출될 수 있었다.

이번 개발에서는 기존 구조를 유지하면서 보고서 검증과 재작성 과정을 개선하였다.

**개선 목표**

1. 종합 보고서의 수치 및 최종 권고 검증
2. CEO·CFO·CTO 개별 보고서 검증
3. What-if 변경 전후 결과 검증
4. 검증 실패 시 LLM 보고서만 재작성
5. 원본 Tool 결과 유지 및 중복 실행 방지
6. 검증에 통과한 최종 보고서 전달

## 2. 수정 및 관련 파일

| 파일 | 개발 내용 |

| `backend/app/systems/k_electronics/agents/advisory.py` | 보고서 검증, 재작성 및 이벤트 처리 |
| `backend/tests/test_mna_executive_summary.py` | 종합·개별·What-if 검증 관련 자동 테스트 |
| `backend/app/library/tools/run_mna_review.py` | 원본 평가 결과와 보고서 검증에 필요한 데이터 제공 |

기존 `run_mna_review` Tool과 LangGraph 기반 Agent 구조는 유지하였다.

## 3. 종합 보고서 사실 검증 강화

### 3.1. 검증 함수

**파일:** `advisory.py`

**함수:** `validate_mna_report()`

LLM이 작성한 경영진 종합 보고서를 실제 `run_mna_review` Tool 결과와 비교하도록 검증 로직을 개선하였다.

검증 대상은 다음과 같다.

| 항목 | 검증 내용 |
|---|---|
| 기업명 | Tool에 등록된 기업명 포함 여부 |
| 매출액 | 실제 재무 수치와 일치 여부 |
| 영업이익률 | 실제 값 누락 및 명시적 충돌 여부 |
| 인수가격 | 실제 요구가격과 다른 수치 기재 여부 |
| 최대 고객 | 주요 고객명 포함 여부 |
| 고객 매출 비중 | 실제 비중 누락 및 명시적 충돌 여부 |
| 최종 인수 권고 | Workflow 권고와 일치 여부 |
| 인수 조건 | 원본 조건 누락 여부 |
| 경영진 관점 | CEO·CFO·CTO 분석 내용 포함 여부 |
| 종합 판단 근거 | 기회·위험·조건에 대한 설명 포함 여부 |

### 3.2. 수치 충돌 검증

기존 주요 수치 포함 여부 확인에 더하여, 보고서가 다른 값을 명시하는 경우를 검사하도록 확장하였다.

주요 검증 결과 코드는 다음과 같다.

- `OPERATING_MARGIN_CONFLICT`
- `ASKING_PRICE_CONFLICT`
- `CUSTOMER_SHARE_CONFLICT`
- `RECOMMENDATION_CONFLICT`

예를 들어 뉴로엣지의 실제 영업이익률이 -8.2%인데 보고서에서 영업이익률을 6.1%로 명시하면 충돌 항목으로 처리한다.

또한 Tool의 권고가 `CONDITIONAL_PROCEED`인데 보고서가 최종 권고를 `PROCEED`라고 명시하는 경우에도 검증에 실패하도록 개선하였다.

이 과정에서는 협상 기준가격과 인수 요구가격을 서로 다른 항목으로 구분하도록 하였다.

현재 충돌 검증은 특정 문장 형식에 대한 정규식 검사이므로, 모든 자연어 표현과 의미적 오류를 완전히 탐지하는 기능은 아니다.

### 3.3. 종합 평가 관점 및 판단 근거 검증

종합 보고서에서는 CEO·CFO·CTO 관점별 평가 내용이 포함되어 있는지 추가로 확인한다.

또한 종합 판단 부분에 긍정 요인, 위험 요인, 선행 조건에 대한 설명이 포함되어 있는지 검사하도록 개선하였다.

이를 통해 단순히 최종 권고 코드만 제시하는 보고서가 아니라, 경영진의 의사결정 근거를 설명하는 보고서를 생성하도록 유도하였다.

## 4. 개별 Persona 보고서 검증

**함수:** `validate_individual_mna_report()`

기존 종합 보고서 중심의 검증을 CEO·CFO·CTO 개별 분석에도 적용하도록 확장하였다.

**검증 내용**

- 기업 데이터와 주요 재무 수치 확인
- 요청한 Persona 구분
- Workflow의 최종 권고 유지
- 인수 진행 조건 누락 방지
- 검증에 실패한 항목 식별

개별 보고서가 검증에 실패하면 기존 평가 결과를 다시 계산하지 않고, 최초 Tool 결과를 근거로 LLM 보고서를 재작성하도록 구성하였다.

재작성 시에는 원래 Persona를 유지하고, 인수 조건 문구를 임의로 변경하지 않도록 지침을 제공한다.

## 5. What-if 보고서 검증

**함수:** `validate_what_if_report()`

What-if 분석은 변경 전후의 입력값과 권고 결과를 비교하는 기능이므로, 일반 M&A 평가와 구분하여 검증하도록 하였다.

**주요 검증 내용**

- 대상 기업 및 평가 Persona
- 변경 전후 인수가격·수익성·고객 비중
- 변경 전후 최종 권고
- 변경 후 인수 조건
- 제거된 인수 조건
- 추가된 인수 조건

예를 들어 인수가격을 2.8조 원에서 2.1조 원으로 변경한 경우, 변경된 가격과 변경 전후 권고가 정확히 설명되도록 검사한다.

가격 관련 조건이 해소되었더라도 고객 집중도, 특허소송, 핵심인력 등 기존 위험이 남아 있다면 해당 인수 조건을 유지하도록 한다.

## 6. 검증 실패 시 LLM 재작성

### 6.1. 기존 처리 방식의 한계

초기 구현에서는 LLM 종합 보고서가 검증에 실패하면 Python Workflow에서 생성한 `verified_report`를 대체 결과로 사용하는 방식이 있었다.

그러나 최종 보고서를 LLM이 작성하는 구조로 일원화하기 위해 재작성 방식을 변경하였다.

또한 전체 Agent를 재실행하면 M&A Tool이 불필요하게 중복 호출될 수 있었다.

### 6.2. 개선된 처리 방식

**함수:** `run_advisory_agent()`

개선된 처리 과정은 다음과 같다.

1. 기존 Agent Workflow 실행
2. 최초 `run_mna_review` Tool 결과 수집
3. LLM이 생성한 보고서 검증
4. 검증 실패 시 원본 Tool 결과를 기반으로 재작성 요청
5. Tool을 바인딩하지 않은 LLM으로 보고서만 재생성
6. 재작성된 보고서를 원본 Tool 결과와 재검증
7. 검증 통과 시 최종 결과 반환
8. 재검증 실패 시 `AgentError` 발생

핵심은 최초 평가 결과를 유지하면서 자연어 보고서만 수정하는 것이다.

```python
revised_message = get_chat_model().invoke([
    SystemMessage(content=system_prompt),
    HumanMessage(content=correction_task),
])
```

위 코드는 처리 구조를 설명하기 위한 축약 예시이다.

실제 구현에서는 종합 보고서, 개별 Persona, What-if에 서로 다른 작성 규칙과 검증 함수를 적용한다.

### 6.3. 중복 Tool 실행 방지

보고서 재작성 단계에서 `run_specialist()`를 다시 호출하지 않고, 기존 Tool 결과를 LLM의 입력으로 제공하도록 변경하였다.

이에 따라 단순 보고서 재작성 목적으로 M&A 평가 Workflow를 다시 실행하지 않도록 개선하였다.

다만 모델 입력 형식 오류로 `ValidationError`가 발생하는 경우의 별도 재시도 처리와, 보고서 검증 실패에 따른 재작성 처리는 구분된다.

## 7. 최종 응답 이벤트 처리

**파일:** `advisory.py`

기존 Agent 실행 과정에서 생성된 이벤트를 수집하고, 검증 실패한 보고서 대신 재검증에 통과한 보고서를 최종 응답 이벤트에 반영하도록 개선하였다.

재작성 시 유지하는 주요 이벤트는 다음과 같다.

- `agent_start`
- `tool_start`
- `tool_end`
- `agent_token`
- `agent_end`

재작성된 보고서는 `agent_token`과 `agent_end.response`에 반영한다.

원본 Tool 호출 기록은 유지하고, 검증에 실패한 최종 보고서를 그대로 전달하지 않도록 처리하였다.

다만 실제 웹 UI에서의 스트리밍 표시 방식과 응답 지연은 별도 통합 검증이 필요하다.

## 8. 코드 정리

보고서 검증과 재작성 관련 기능이 정상적으로 작동하는 것을 확인한 뒤, 기능 변경 없이 불필요한 코드를 정리하였다.

**`advisory.py`**

- 개별 Persona 재검증 실패 구간의 임시 `print()` 제거
- 기존 `AgentError` 처리 유지
- 평가 및 보고서 생성 로직 유지

**`run_mna_review.py`**

- What-if 반환 딕셔너리의 중복된 `query` 키 제거
- 기존 반환 필드 및 UI 호환 구조 유지

이번 정리에서는 공용 LangGraph, Super Agent 및 A2A 통신 코드를 수정하지 않았다.

## 10. 개발 결과 및 한계

이번 개발을 통해 종합 보고서뿐 아니라 개별 Persona와 What-if 보고서에도 사실 검증 및 재작성 기능을 적용하였다.

**주요 성과**

- 보고서 유형별 검증 함수 구성
- 주요 수치·권고·인수 조건의 충돌 검증
- 검증 실패 시 LLM 기반 보고서 재작성
- 기존 Tool 결과 재사용을 통한 중복 실행 방지
- 최종 응답 이벤트의 검증 결과 반영
- 불필요한 디버깅 출력 및 중복 키 정리
- 경영자문 관련 자동 테스트 75개 통과

**남아 있는 한계**

- 정규식 기반 검증은 모든 의미적 오류를 탐지하지 못함
- 가격 인하율과 같은 파생 수치의 모든 계산 오류를 검사하지는 않음
- 실제 LLM의 질문 표현에 따라 보고서 내용이 달라질 수 있음
- 검증 실패 및 재작성 상황의 다양한 모델별 반복 실행이 추가로 필요함

현재 기능 개발 범위에서는 기존 M&A 평가 Workflow와 LLM 보고서 검증·재작성 구조를 유지하고, 추가 기능 개발보다는 실제 실행 안정성 확인을 우선한다.

**검증 범위:** 경영자문 관련 자동 테스트 75개 통과. 전체 프로젝트 통합 테스트 및 웹 UI 검증 결과와는 구분함.
